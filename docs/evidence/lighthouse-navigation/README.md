# Home navigation Lighthouse investigation

This evidence concerns Home `/`, measured with every Lighthouse category. It does not establish results for every Article URL, a deployed candidate, CI, merge, or public CDN performance. GitHub Pages and the official Gravatar card remain the chosen hosting/provider boundaries.

Mobile Performance is **71**, FCP 3.815 s, LCP 5.345 s, TBT 5 ms and CLS 0. Desktop Performance is **100**, FCP 0.539 s, LCP 0.599 s, TBT 0 ms and CLS 0.0211. Build each checkout with `SITE_URL=https://oomia.github.io BASE_PATH=/ DOCS_CHECKOUT_MODE=main vp run --filter web build`, then run from the candidate repository:

```sh
vp run --filter web test:lighthouse \
  --baseline-dist /absolute/path/to/baseline/apps/web/dist
```

The harness runs three navigations per revision and viewport, always in a new extension-free Chrome profile. Lighthouse is pinned to **13.4.1**. Desktop is 1440×1000 / DPR 1, mobile 390×844 / DPR 3. Explicit simulated throttling is identical between revisions: desktop RTT 40 ms / 10,240 Kbps / CPU 1×; mobile RTT 150 ms / 1,638.4 Kbps / CPU 4× (additional DevTools throughput/latency values are stored in the configuration). Both builds use the same local gzip level 6 static server with `Cache-Control: max-age=600`. This controls compression/cache differences; it does not reproduce Pages CDN latency, HTTP/2, TLS or hosting response headers. External providers are real and unmocked, so their availability remains variable. Provider requests and Lighthouse warnings are retained per run.

The accepted measurements use installed Google Chrome 155.0.8059.80 in headless mode; the latest supplied reports use host Chrome 154. All twelve accepted navigations use the same installed version. This browser difference, explicit emulation and local serving prevent treating the supplied public score versus the local candidate score as a controlled before/after comparison.

Ignored output is `test-results/lighthouse-navigation/`: raw Lighthouse JSON, first-run compressed traces, individual keyboard/coverage records and `summary.json`. Open a raw report with the Lighthouse report viewer; decompress a `.trace.json.gz` file to load its trace in Chrome DevTools. `--variants baseline` or `--variants candidate`, `--modes desktop,mobile`, `--runs 3`, `--output /absolute/path`, `--base /preview`, `--interactions false` and `--lighthouse false` support isolated reruns. `LIGHTHOUSE_CHROME_PATH` selects an installed compatible Chrome; otherwise the installed Playwright Chromium is used. Performance runs must be serialized with builds and browser regression suites.

The existing **Manual OS compatibility** workflow (`os-compatibility.yml`) provides a `performance` profile that runs this same harness on one Ubuntu runner. Select the candidate branch and provide full Site baseline and prepared Docs commit SHAs; both builds consume that exact Docs checkout in `resolved` mode. It reuses the existing private-Docs checkout credential, installs one shared Playwright Chromium, and measures three navigations per desktop/mobile variant without the separate interaction profile. The artifact contains raw reports, traces, `summary.json` and an `audit-ledger.json` inventory retaining manual, N/A and unscored entries. Its step summary reports FCP/LCP and font transfer medians. This workflow does not deploy either build, establish a public-host result, or automatically decide an audit's cause/disposition from its score. Run it only when a performance-relevant change warrants comparison; ordinary regressions continue to use existing CI. Its `quality` profile runs the existing theme, CSP and font-loading regressions on Ubuntu only; `compat` and `full` retain their existing three-OS coverage. For a branch carrying this change, dispatch the already registered workflow with `gh workflow run os-compatibility.yml --ref <candidate-branch> -f profile=performance -f baseline_revision=<full-site-sha> -f docs_revision=<full-prepared-docs-sha>` (or `-f profile=quality` for the focused browser checks).

The desktop totals are 737,924 →698,887 B with 56 requests in both. Native iframe lazy loading uses a browser distance threshold: at desktop the card is about 3,113 px below the initial document top and already makes nine Gravatar requests before scrolling; on mobile at about 5,655 px it makes zero before scrolling and nine after. Native lazy loading therefore demonstrably defers the mobile card, while it does not guarantee zero initial desktop provider traffic. The official provider's PNG/CSS policies remain a residual even where the new external-frame boundary no longer produces the same image/unused-CSS audit finding.

All six accepted candidate runs pass LCP discovery and report no forced-reflow attribution; `identical-links-same-purpose` is now N/A. `unused-css-rules` and `image-delivery-insight` score 1, which does not establish that the provider changed its internal images or styles. Remaining measured findings include render-blocking CSS (candidate mobile estimated 1.2–2.56 s), unused JavaScript (about 57 KiB desktop / 60 KiB mobile), dependency chains and cache estimates (589 KiB desktop / 415 KiB mobile). The source-map table is empty in all six clean candidate runs. Desktop lists no long tasks; mobile lists one document-attributed 56–82 ms task per run with TBT still 0. These task tables alone do not identify a removable Site function.

Candidate coverage increases when the required interactions run: React renderer 28.90% →35.89% desktop and 28.12% →35.83% mobile; SiteFrame 33.91% →34.52% in both. The preserved branches serve shared framework and interaction behavior, and this finite coverage flow does not prove remaining code is dead. Both viewport profiles successfully exercise keyboard theme activation, tag first/last navigation, Escape return, selected filter state and the explicitly constrained tag-overflow focus return. Both record zero page errors and no horizontal document overflow. No speculative runtime deletion was made to reduce an unused-byte estimate.

## Keyboard, DOM and manual audit boundaries

The harness exercises theme with Enter; tag-picker ArrowDown, End, Escape, Enter and selection; and tag-overflow open/Escape/focus return. It records the first 16 Tab stops, accessible names, roles/landmarks, heading order, document width, structured-data JSON, featured-image attributes and Gravatar request timing. When real tags fit naturally, the overflow branch is exercised with an explicitly recorded 40 px width constraint; those stress observations are excluded from Lighthouse navigation measurements. JavaScript coverage uses V8's most-specific nested execution ranges and UTF-16 source units, not compressed transfer bytes. It covers a finite interaction sequence and does not establish that remaining code is removable.

These manual audits are not silently converted to PASS by an automated score of 100. No screen-reader, merge, deployment or public candidate result is claimed here.

Local regression verification comprises 158 passing unit tests, the 50-test full browser suite, a subsequent 10-test focused check after the tag animation-frame lifetime guard, and two final focused CSP browser checks after preserving native MDX iframe destinations. The CSP checks cover external iframe loading, normal theme/hydration and blocking unauthorized inline script. A final 24-page production build, Astro checks over 80 files and static CSP inspection over 112 built files also pass. Non-root `BASE_PATH` smoke checks cover the 24-page build, navigation/geometry and four screenshots; that smoke preceded only the final removal of the restrictive iframe directive, so its content/geometry evidence is distinct from the final CSP-policy check. These are local checks; they do not establish CI, merge or deployment.
